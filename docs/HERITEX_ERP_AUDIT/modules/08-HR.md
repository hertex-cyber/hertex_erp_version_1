# 08 — HR & Payroll

**Module owner:** HR
**Rank:** "adequate but statutorily correct" per `Best-Product-Plan §3` — do NOT over-invest in UX here; DO get PF/ESI/TDS right
**Current state:** tables exist; payroll uses **flat hardcoded percentages** with no ceilings, slabs, or journals — not statutory
**Date:** 2026-07-17

---

## 1. Purpose & scope

Owns employee lifecycle: departments, employee master, attendance, leave, payroll runs, payslips. The plan explicitly directs: HR/payroll must be **statutorily correct** (PF/ESI/TDS) and reliable; it is **not** a differentiator. Spend on correctness and audit, not polish.

**In scope:** employee master, attendance, leave with balance, payroll with PF/ESI/TDS, payslips, payroll journal to Finance, compliance reports.
**Out of scope (deliberately):** recruitment ATS, performance appraisals, shifts/rostering UI, employee self-service portal (all v2 — plan Phase reschedule).

**Headline:** payroll *runs* but is **not statutory**. Flat percentages with no ceilings and no employer side will produce wrong PF/ESI for any employee above the wage ceiling and wrong TDS for anyone not in the 5% flat band. This is exactly the "statutorily correct" bar the plan sets — currently unmet. Any demo or client use would create a compliance liability.

### 3.2 The statutory-config table
The current hardcoded rates must move to `hr_pf_esi_tds_rules` — statutory figures change with budget notifications, and a single config row per effective period is the only maintainable design. It also gives an audit trail of "which rules produced this payslip".

## 4. State machines

### 4.1 LeaveRequest
```
pending  --approve--> approved   guard: approver has authority, balance available
pending  --reject-->  rejected   guard: reason recorded
pending  --cancel-->  cancelled  (by requester before approval)
approved --use-->     used       (attendance marked as leave)
```
### 4.2 PayrollRun
```
draft      --generate-->  processing   (snapshot active employees + attendance, compute)
processing --finalize-->  processed    guard: all payslips balanced, run locked   → payslips immutable, journal posted
processed  --close-->     closed       (period closed in Finance)
processing --revert-->    draft        (only before processed; deletes generated payslips)
```
### 4.3 Payslip
```
generated --pay-->  paid   guard: run processed, bank details present   → salary payment journal
generated --void--> void   (correction only via new payslip)
```

## 6. Business rules

- **HR-01** — Payroll applies PF: employee 12% of basic+certain allowances **up to the wage ceiling**; employer EPS 8.33% (capped) + EPF 3.67% (approx) — exact employer split config-driven. *(Currently flat 12% of full salary — wrong.)*
- **HR-02** — ESI: employee 0.75% / employer 3.25% of gross **up to the wage ceiling**. *(Currently 0.75% only, ceiling hardcoded 21000 — needs current-year verification.)*
- **HR-03** — TDS computed from **income-tax slabs** (via the configured slab table with standard deduction), not a flat 5%. *(Currently flat 5% — wrong.)*
- **HR-04** — Provident fund and professional tax are state/ceiling-specific; `hr_pf_esi_tds_rules` is the single source.
- **HR-05** — A payroll run snapshots employees + attendance at `generate`; edits after `finalize` are impossible (immutable payslips, I4).
- **HR-06** — `finalize` posts a **salary journal**: debit Salary Expense (split: basic/HRA/special + employer contributions), credit PF/ESI/TDS/PT payable accounts and Net Payable. *(Missing — payslips exist but nothing reaches the ledger.)*
- **HR-07** — Leave approval requires available balance; `pending` requests hold balance.
- **HR-08** — Attendance impacts payroll only if the policy says so (full-month salary vs worked-days basis, configurable).
- **HR-09** — Aadhaar/PAN/bank stored masked; visible only to HR roles (D4).
- **HR-10** — Every payslip records which statutory-rule row produced it (audit + future recompute).

## 7. Workflows (end-to-end)

### 7.1 Monthly payroll (target)
1. Run drafted for period; `generate` snapshots active employees + attendance.
2. Statutory engine applies PF/ESI/TDS/PT per `hr_pf_esi_tds_rules`.
3. Payslips reviewed (variance vs last month).
4. `finalize` → lock runs, post salary journal to Finance (HR-06), publish `payroll.processed`.
5. `pay` → mark paid per employee, record payment, publish `payslip.paid`.
6. Compliance reports generated (PF/ESI/TDS/PT returns).

### 7.2 Leave → attendance → payroll
Leave request → approve → balance decremented → attendance row `status=leave` → payroll excludes leave days (per policy).

## 8. Accounting impact (the missing journal table)

| Event | Debit | Credit |
|---|---|---|
| Salary accrual | Salary Expense (basic+HRA+special+OT) | PF Employee Payable, ESI Payable, TDS Payable, PT Payable, Net Payable |
| Employer contributions | Salary Expense (employer PF + ESI) | Employer PF Payable, Employer ESI Payable |
| Salary payment | Net Payable | Bank |
| Statutory remittance | PF/ESI/TDS/PT Payable | Bank |

**None of these exist today.** Payroll runs produce payslips and nothing else — the numbers never touch Finance, so the trial balance will not include payroll and the cash-flow forecast will not see salary outflows.

## 11. Non-functional & security

- **Correctness:** statutory rates are config, verified by golden-master tests against known EPFO/ESI examples.
- **Performance:** payroll for 500 employees < 5 s.
- **Concurrency:** `finalize` uses a DB lock to prevent double-finalize.
- RBAC: `hr.department.*`, `hr.employee.*`, `hr.attendance.*`, `hr.leaverequest.*`, `hr.payrollrun.*`, `hr.payslip.*` (exists) + add `hr.compliance.read`.
- **Field security (D4):** salary, PAN, Aadhaar-last4, bank account visible only to payroll/HR roles; masked in all API responses otherwise.
- DPDP: employee personal data — consent + retention; Aadhaar last4 only, never full.
- Audit: every payslip generation, finalize, pay, rule change.

## 14. Implementation plan

| Milestone | Scope | Acceptance |
|---|---|---|
| **M1 (statutory engine)** | `hr_pf_esi_tds_rules` config; correct PF/ESI/PT/TDS with ceilings & slabs; golden-master tests | HR-01..04 tests against EPFO examples |
| **M2 (employer side + journal)** | employer contributions; salary journal posting on finalize; payable accounts | HR-06 tests; GL ties |

| **M5 (compliance + reports)** | PF/ESI/TDS/PT report generation; variance report | statutory report matches ledger balances |

Order: **M1 (must) → M2 (must) → M3 → M4 → M5**. M1/M2 are release blockers — payroll that isn't statutory and doesn't hit the ledger is worse than no payroll.

## 15. Test plan

- Golden master: employee at ₹18,000 → PF 12% of 15,000 ceiling (not 18,000); ESI 0.75%/3.25% (M1).
- TDS: salary bands 5%→30% via slab table (BR-HR-03).
- Employer contributions computed and in journal (M2).
- Leave balance decremented on approval; insufficient balance rejected (M3).
- Double-finalize blocked; payslip immutable after finalize (M4).
- Idempotency: re-generate after revert only.
