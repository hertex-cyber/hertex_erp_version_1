## 1. Purpose & scope

Owns the AI platform: the "Ask Hertex" conversational interface (Tier 2), the Tier 1 embedded-intelligence models (scoring/forecasting per module), and the Tier 3 agentic actions (writes performed through the workflow engine). The rules A1–A5 from `00-MASTER-ARCHITECTURE.md §10` are binding here.

**In scope:** intent engine, LLM integration (Claude) with function-calling, read-only query safety, model serving for Tier 1, action registry for Tier 3, cost/guardrails.
**Out of scope (v1):** building our own model training infra (use sklearn/statsmodels + hosted Claude), general web-crawling agents, multi-agent frameworks.

## 3. Domain model

### 3.1 The design (three layers, per Technical Plan §8)

```
LAYER 1 — Intent & query layer (Tier 2)
  intent_map: intent -> allow-listed ORM query builders (already partially exists as _detect_intent)
  LLM wrapper: Claude with function-calling; tools = the intent_map entries
  Safety: user prompt → LLM chooses a tool + params → code validates/executes ORM → formats answer.
          The LLM NEVER runs SQL and NEVER sees raw query strings.

LAYER 2 — Embedded models (Tier 1)
  model_registry: name -> trained artifact (pickle/onnx) + feature extractor
  lead_scorer     (module 07)  — logistic regression/GBM on deal-age, engagement, source, size
  reorder_forecaster (module 03) — exponential smoothing / moving average on StockMove
  anomaly_detector (module 01) — journal outlier detection
  attrition_risk   (module 08) — tenure/leave/salary features
  schedule: nightly batch via Celery; inline <200ms for small sets

LAYER 3 — Actions (Tier 3)
  action_registry: action_type -> handler with scope + approval policy
  draft_po, draft_whatsapp_followup, draft_invoice, auto_reconcile, draft_campaign
  Each action is a workflow-engine action type (module 15/16 or engine), inherits RBAC + audit.
```

### 3.2 New tables
```
ai_model_runs       model_name, version, ran_at, rows_processed, metrics_json, artifact_ref, status
ai_predictions      model_name, entity_type, entity_id, score, features_json, model_version, created_at
ai_conversations    user_id, question, intent, model_used, latency_ms, tokens_used, feedback, created_at
ai_actions          action_type, entity_type, entity_id, actor_user_id, on_behalf_of,
                    status [proposed|approved|rejected|executed|failed], payload_json, decision_time
```

## 4. State machines

### 4.1 AI action (Tier 3) — the critical one
```
proposed  --approve-->  approved   (human, or pre-approved policy)   → executor runs with scoped write
approved  --execute-->  executed   guard: action handler validates scope + idempotency
proposed  --reject-->   rejected   guard: reason logged
executed  --revert-->   reverted   (compensating action where supported)
```
Every Tier 3 action is audited with `actor_user_id` + `on_behalf_of` (MA I6).

### 4.2 Model run
```
queued  --start-->  training/running
running --ok-->     completed   (store metrics + version)
running --fail-->   failed      (keep previous version; alert)
```

## 6. Business rules

- **AI-01** — The LLM never runs SQL; it selects from the allow-listed intent map; code executes the query (A2).
- **AI-02** — Every query is tenant-scoped and RBAC-filtered in code after the model's choice (A1).
- **AI-03** — Tier 3 writes happen **only** through approved actions; no direct model write (A3).
- **AI-04** — Every Tier 1 score exposes its top-3 features (`features_json`) (A4).
- **AI-05** — Tabular problems use classical models, not LLMs (A5); cost guard per tenant.
- **AI-06** — Actions are idempotent (retry-safe) and revertible where meaningful.
- **AI-07** — `Lead.score` is written only by the scorer job, never by hand (module 07 CR-02).
- **AI-08** — Every AI response carries a confidence/source reference where available.

## 7. Workflows (end-to-end)

### 7.1 Ask Hertex (Tier 2, upgraded)
1. User asks "outstanding receivables from Aspects?" → `POST /ai/ask`.
2. LLM maps to the `receivables` tool with params (customer filter) → tool returns scoped rows.
3. Answer formatted with amounts + a drill-down link; `ai_conversations` logged with latency/tokens.
4. Feedback captured → fine-tune prompts/tools.

### 7.2 Tier 1 nightly batch
1. Beat triggers `lead_scorer` → computes scores → writes `ai_predictions` + updates `Lead.score` (via service, RBAC'd).
2. Metrics stored; drift check (score distribution shift) alerts.

### 7.3 Tier 3: reorder → draft PO
1. `stock.low` event + forecast says SKU will stock out.
2. Action `draft_po` proposed → Procurement queue shows the pre-filled PO.
3. Buyer approves (approval_limit chain intact) → PO created → `po.approved`.
4. Audited: who proposed (AI, on_behalf_of buyer), who approved.

## 11. Non-functional & security

- **Latency:** Ask < 3 s (LLM) / < 200 ms (rule fallback); batch models nightly.
- **Cost:** per-tenant token budget, per-month alert; tabular models preferred.
- **Reliability:** if the LLM is down, fall back to the rule engine (current behaviour) with a "reduced accuracy" note.
- RBAC: `ai.assistant.use` (exists); action approvals use the owning module's permission codes.
- **Security:** never trust model output for authorisation (A1); prompt-injection defence: tools are allow-listed, params validated.
- DPDP: AI logs may contain personal data — masked in `ai_conversations` where possible; retention 90 days.
- Audit: every action + every model run.

## 15. Test plan

- Tenant isolation: user A can't see user B's receivables via Ask (M1).
- Score determinism + feature exposure (M2).
- Forecast accuracy vs simple baseline (M3).
- Action: draft_po proposed → approved → PO created, idempotent re-approve (M4).
